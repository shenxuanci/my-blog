# 台账去掉指纹重置，逐门计数改为真正的累计仪表盘

ADR 0016 退役了「攒够 N 天 → 解锁 `objectivity active` / 解锁补源」这层语义，但保留了台账的全部机制：每日记录、指纹重置、失败清零、缺口冻结。保留的理由是「台账本身是有用的质量仪表盘」。

2026-08-16 的对抗式审查指出，保留下来的指纹重置正在让它**不成为**仪表盘。共享运行时指纹覆盖 `daily_news.py`、`rollout_validation.py`、`article_extractor.py`、`requirements.txt` 四个日常会改的文件，`RUNTIME_RESET_GATES = GATES` 让指纹一变就重置全部五门，而管线平均每 1-3 天就有一次改动。结果是一个读数几乎恒为个位数、且不通往任何判定的计数器。

这一点在本次审查过程中现场复现了一次：为记录本决策而给 `daily_news.py` 加的一段**纯注释**，就会让下一次 publish 把五门再次清零——指纹哈希的是整个文件字节，注释和逻辑改动等价。

## 决定

从 `compute_streaks` 中移除指纹重置，删除 `RUNTIME_RESET_GATES` 与 `TRAJECTORY_UI_RESET_GATES` 两个常量。指纹仍然逐日记录并渲染进评论，只是不再触发归零——它的角色从闸门降为诊断信息。

指纹重置的存在理由是「代码变了，之前攒的连续天数不能算」。这个理由只在「连续天数通往一个开关」时成立；开关已由 ADR 0016 移除，而仪表盘要读的是趋势而非连续性，此时重置只剩破坏信息一个效果。

## 刻意不改的部分

- **`window_start()` 保留它自己的 runtime 变更重启。** 它喂的是 `evaluate_enrich` 的基线比较（`enrich_baseline`），那里「改动前后的数据不能混」是真的成立的语义。它和逐门计数是两个不同的 sink，不是同一个 sink 的两条入口——审查时先按「漏一条入口等于没改」的直觉打算一起改，读完调用点后撤回了这个判断。
- **失败清零保留。** `publication == "failure"` 清零 `CONSECUTIVE_GATES` 与指纹无关：当天没发出去，连续性确实断了。
- **缺口冻结保留，且经核实本来就是正确的。** 缺口日的全部门记为 `neutral`，`_apply_gate` 对 `neutral` 返回原值，因此计数既不推进也不清零。`build_gap_state` 里的 `streaks` 字段只是写进评论的快照，不参与重算。

## 代价与被接受的风险

**历史数字会变。** `compute_streaks` 每次都从 Issue #15 的全部逐日评论重算，所以去掉重置后，重算出的历史计数不再等于过去评论里存下的快照。旧评论的快照保持原样不动，今后展示的是重算后的累计读数。台账历史本身是完整保留的（逐日 append-only，每天的 `fingerprints` 原值都在），所以这次改动不丢任何信息，只是换了一种读法。

`test_live_v1_comments_migrate_without_inventing_gate_evidence` 因此调整了 trajectory 的期望值，并把注释改清楚：那条测试钉的是**迁移契约**（判定原样保留、尚不存在的门保持 neutral），不是计数算术。

原先断言重置行为的两条测试反转为断言重置**不再发生**，因此重新引入重置会让测试失败。

## 与既有决策的关系

本决策取代 ADR 0016 中「台账保留指纹重置」这一项。ADR 0016 的其余决定不受影响，仍然有效：`objectivity.mode` 永久 `interim`、shadow 按累计样本封顶且 `shadow_status` 保持零网络 I/O、逐门进度不显示分母、45 条夹具三轮门与配对成本门降为手动探针。
