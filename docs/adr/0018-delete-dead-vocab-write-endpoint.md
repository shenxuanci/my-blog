# 删除已停用单词本的写端点，历史数据原地保留

单词本自 2026-07-10 停用（`config.yaml` 的 `vocab.enabled: false`），前端界面已移除。当时记录的决定是「历史数据与 `api/vocab.js` 保留」，为的是保住一条恢复路径：把 `enabled` 改回 true、前端从 git 历史找回界面。

2026-08-16 的对抗式审查指出这条决定留下了一个不必要的面：`api/vocab.js` 仍然完全可路由、可写，能反复把数据写进公开 Git 仓库。它不是越权——认证走 `requireAdminWrite`，门槛和 `adminArticles.js` 等活跃接口完全相同，持有 `ADMIN_TOKEN` 的人本来就能写仓库。问题在于**功能已死而接口活着**：`enabled: false` 让 `build_vocab` 在 `daily_news.py:7381` 直接 return，所以管线侧零 token 成本、零读写；唯一还在运行的就是这个没有任何前端调用者的写端点。

## 决定

删除 `api/vocab.js`。保留 `source/news/data/vocab-book.json`（16 条真实词条）与 `source/news/data/vocab/*.js` 四个按日文件，也保留 `daily_news.py` 里的 `VOCAB_*` 提示词与 `build_vocab` 子系统。

恢复路径改为：把 `enabled` 改回 true，并从 git 历史找回 `api/vocab.js` 与前端单词本界面。接口和界面用的是同一个恢复机制，因此这条路径与 2026-07-10 那条决定是自洽的——被推翻的只有「保留接口」这一项，不是「保留恢复能力」。

## 被否决的替代方案

- **保留文件，handler 直接返回 410 Gone**：Vercel 上不存在的路由本来就返回 404，专门留一个 handler 去返回 410 是多写代码换更少的语义。
- **连数据和管线子系统一起删**：这会推翻 2026-07-10 关于保留历史数据的决定，销毁 16 条手工收集的词条，并让 ADR 0010 与 ADR 0012 的正文指向不存在的代码。删数据在安全上买不到任何东西——让人不安的是可写端点，不是那 16 个词。
- **保持现状**：成本确实近似为零，但「死功能带着活的写权限」是一类会被遗忘的面，而删掉它的代价只是一次 git 历史回捞。

## 代价与被接受的风险

**随接口一并消失的还有它承担的数据校验。** 原 `api/vocab.js` 在读取时要求 `version: 1` 且 `words` / `pending` 为对象数组，损坏时报错并禁止覆盖，明确不允许「因功能停用就把原数据静默当空书」。管线侧的 `load_vocab_book`（`daily_news.py:7200`）行为相反——缺失或损坏一律返回空册。当前 `enabled: false` 下 `build_vocab` 先行 return，不会读到那个文件，所以这个差异现在没有后果。**但恢复功能时必须把那条校验一起找回**，否则一个损坏的 `vocab-book.json` 会被静默当作空书并被覆盖，16 条词条只剩 git 历史里有。

`.vercelignore` 与 `_config.yml` 对 `vocab-book.json` 的排除保持不变，数据仍不进静态产物。`test_admin_api.mjs` 中「个人状态文件排除在静态部署之外」那条测试继续覆盖它。

## 与既有决策的关系

- **ADR 0010** 正文把 `vocab.js` 列在走 `requireAdmin()` 的接口里。那段是对当时状态的历史记述，原文不改；本决策只取代其中「`vocab.js` 是保留接口」这一项事实。
- **ADR 0012** 第 52 行把 `VOCAB_*` 列为停用功能、未纳入对象包裹改造。提示词仍在 `daily_news.py` 里，该段结论不受影响，仍然有效：若将来重新启用，必须先切到对象包裹契约。
